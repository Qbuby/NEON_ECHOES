# NEON ECHOES — architecture

## What this document is

The decisions that shape how the game is built, and why. Written so a new agent
can start work without re-deriving them.

## 1. The one decision everything else follows from

The twelve concept images in `asserts/mind_map` are **isometric 2:1 with real
building height**. The previous build rendered a **flat orthographic grid**.
Five independent reviewers scored that build 1.8–2.4 / 4.0 and every one named
composition and depth — they were describing a camera mismatch.

So the renderer was replaced (ADR-001) and the simulation was kept.

## 2. Layering

```
data/            authored content (JSON)      — no code
  districts/     level descriptions IsoWorld reads
  *.json         weapons, enemies, skills, cyberware, items, quests, dialogue, endings

src/systems/     pure gameplay logic (RefCounted, no Node, no rendering)
                 combat, enemy AI, stealth, hacking, progression, quests,
                 endings, saves, weapon runtime
                 unit-tested headless; reusable by any renderer

src/world/       scene construction and rendering
  iso_grid       projection, picking, depth key       (18 unit tests)
  iso_world      floor / wall / prop / actor assembly
  iso_lighting   neon light pools
  actor_sprite   animated 2:1 actors from a JSON frame table
  iso_demo       the playable scene

src/autoload/    cross-cutting services
                 log, game state, audio, playtest harness, ux probe

tools/           asset pipeline (Python, deterministic, no network)
  gen_iso_tiles.py     floor diamonds, wall prisms, facades, roofs
  gen_iso_props.py     street furniture, signage, lamps
  gen_iso_actors.py    character sheets (4 facings x 5 animations)
  gen_district.py      composes a district from the above
```

### The rule

**Systems never import rendering. Rendering never contains rules.**

A system takes numbers and returns numbers. `Progression.derived_stats()`
returns a dictionary; it does not touch a node. `EnemyAI.tick()` returns
`{action, state}`; the renderer decides what that looks like. This is why the
921 LOC of gameplay logic survived the renderer rewrite untouched, and why the
79-assertion suite still runs headless.

## 3. Geometry, and why it constrains level design

A 64×32 diamond. `IsoGrid.project()` maps grid → screen; `unproject()` inverts
it; `depth_key()` orders the painter's algorithm.

**Only the south and east faces of a block are visible.** A north-south street
therefore shows facades on its west side only; the east side turns its hidden
west wall to the street and presents a bare roof. Every concept image is
composed around this — 企业核心区街道 has detailed facades on the left and an
open walkway right, 工业贫民区 has the wall left and roofline clutter right.
Level layout must be authored with the visible faces in mind.

**A wall is a prism, not a rectangle.** The two faces are parallelograms. Drawing
them as 64-wide rectangles produced triangular border artefacts; that was
observed, fixed, and is now generated from exact pixel maths.

**Facades are flat-topped; roofs supply the diamond.** Each facade tile carries
only the lower V of its diamond, so adjacent facades meet in a straight line.
A facade that includes its own full diamond makes the roofline sawtooth.

## 4. Depth sorting

One sorted list across floors, walls, props and actors. Sorting by screen y is
wrong for isometric — two cells on the same row can share a y, and a tall object
behind a short one must draw first. The key is `(x + y)` ascending, plus a small
height term, plus per-kind offsets so floor < roof < facade at the same cell.

**All sprites must be children of the same node.** Four separate root nodes at
equal `z_index` paint in child order, which buried the facades under floor tiles
until this was fixed.

## 5. Asset pipeline

Everything is generated by deterministic Python with a fixed seed. No network,
no manual painting, no binary blobs checked in without a recipe.

* Exact pixel geometry (diamonds, prisms, parallelograms) is computed, not drawn
  with a general image tool — the shapes are too precise.
* Art is authored to a per-district palette. Palette values are the contract
  between the tile set, the props, the characters and the UI.
* Measurable art direction: the concept frames carry 3–6% of pixels above
  luminance 180 and p95 near 175. `tools/measure_frame.py` reports the same
  statistics for a render, so "does it look like the reference" is a number, not
  an opinion.

## 6. Verification loop

| Gate | Command | Bar |
|---|---|---|
| Projection maths | `gd --headless -s tests/test_iso_grid.gd` | 18/18 |
| Gameplay systems | `gd --headless -s tests/run_suite.gd` | 79/79 |
| Playthroughs | `gd --headless -s tests/run_playthroughs.gd` | 3/3 |
| Frame statistics | `python tools/measure_frame.py <png>` | within concept range |
| Screenshot | `gd -s tests/shot_iso.gd` | 1920×1080 |

The loop an agent runs: change → build → screenshot → measure → look → repeat.

## 7. What is deliberately not built

* No custom engine, editor, or runtime — Godot 4 does that.
* No agent platform — this is a game, developed by an agent.
* No reimplementation of what Godot provides (scene tree, input, audio, export).
* No abstraction for its own sake: `IsoWorld` is one file because it is one job.
